# РОЗДІЛ 1. АНАЛІЗ ІСНУЮЧИХ АНАЛОГІВ

## 1.2 Інженерний конкурентний аналіз

### Todoist

#### Архітектурний підхід

Todoist реалізовано як багатоклієнтську систему керування завданнями з централізованим серверним API та механізмами синхронізації між web-, desktop- і mobile-клієнтами. Повна внутрішня структура backend-компонентів у відкритій документації не розкривається, тому однозначна класифікація системи як монолітної або мікросервісної не здійснюється.

Для first-party клієнтів застосовується спеціалізований механізм синхронізації з підтримкою batching та incremental sync. Такий підхід дає змогу зменшити кількість мережевих запитів і передавати лише дані, змінені після попередньої синхронізації.

#### Протоколи передачі даних та API

Todoist надає REST API та окремий Sync API. Для авторизації інтеграцій застосовуються OAuth і Bearer Token. Операції синхронізації виконуються через HTTP POST. Платформа також підтримує Webhooks для реакції зовнішніх інтеграцій на зміни без постійного polling.

#### Стек даних і консистентність

Конкретні внутрішні СУБД та механізми реплікації у відкритій документації не специфіковано. На рівні клієнт-серверної взаємодії використовується модель синхронізації із `sync_token`, що дає змогу отримувати лише зміни після останньої успішної синхронізації.

Для first-party клієнтів застосовуються optimistic updates, за яких локальні зміни можуть бути відображені до остаточного підтвердження сервером. Такий механізм зменшує сприйману затримку, але потребує додаткової логіки узгодження станів.

#### Масштабованість і Technical Bottlenecks

Batching та incremental sync зменшують кількість API-викликів і обсяг переданих даних. Водночас повна синхронізація великих наборів даних може супроводжуватися підвищеною затримкою. Основним архітектурним компромісом є складність механізму синхронізації та необхідність коректного узгодження тимчасових і серверних станів.

### Motion

#### Архітектурний підхід

Motion функціонує як хмарна багатокомпонентна система керування завданнями, календарями та проєктами. Повна внутрішня backend-архітектура публічно не розкривається, тому точна класифікація архітектурного патерну не здійснюється. Водночас система використовує окремі інфраструктурні сервіси для обчислювальних операцій, фонової обробки, моніторингу та роботи з даними.

#### Протоколи передачі даних та API

Motion надає HTTP API версії `v1` для роботи із завданнями, проєктами, користувачами та розкладами. Взаємодія здійснюється через REST-подібні endpoints. Для автентифікації API-запитів застосовується `X-API-Key`. Для вибірки великих наборів даних використовується cursor-based pagination.

#### Стек даних і консистентність

Публічна документація не деталізує внутрішню транзакційну модель або конкретні механізми реплікації. Водночас відкриті відомості вказують на використання окремих керованих сервісів баз даних, аналітичного зберігання та фонового виконання задач.

Модель даних організовано навколо tasks, projects, users і schedules. Параметри дедлайнів, тривалості, статусів і автоматичного планування використовуються для перерахунку розкладу.

#### Масштабованість і Technical Bottlenecks

Cursor-based pagination зменшує навантаження під час отримання великих списків. Асинхронна фонова обробка дає змогу не блокувати синхронні користувацькі запити під час виконання складних workflow.

Основним архітектурним компромісом є залежність від значної кількості зовнішніх інфраструктурних компонентів, що збільшує складність інтеграції, observability та керування відмовами між сервісами. Операції автоматичного перепланування також підвищують обчислювальне навантаження через необхідність обробки часових обмежень, дедлайнів і конфліктів календаря.

### Sunsama

#### Архітектурний підхід

Sunsama реалізовано як хмарну інтеграційно-орієнтовану систему персонального планування, що агрегує завдання, календарні події та дані зовнішніх сервісів. Повна внутрішня backend-архітектура у відкритій документації не розкривається.

#### Протоколи передачі даних та API

Для обміну даними із зовнішніми платформами використовуються HTTP-based API інтегрованих календарних і task-management сервісів. Деталі внутрішніх протоколів взаємодії, використання gRPC, GraphQL або WebSockets публічно не специфіковано.

#### Стек даних і консистентність

Конкретна внутрішня СУБД та механізми реплікації не розкриваються. Основною інженерною задачею є підтримання узгодженого стану між локальним планом користувача та зовнішніми джерелами даних.

Наявність кількох інтеграцій потребує обробки конфліктів, дублікатів, затримок синхронізації та повторного виконання невдалих операцій.

#### Масштабованість і Technical Bottlenecks

Масштабованість системи значною мірою залежить від зовнішніх API, їх rate limits і доступності. Для одночасної синхронізації великої кількості облікових записів необхідна ефективна фонова обробка й retry-механізми.

Основними технічними обмеженнями є залежність від сторонніх сервісів, ризик втрати актуальності даних у разі недоступності інтеграцій та складність забезпечення консистентності між кількома джерелами.

## Аналітичний висновок підрозділу 1.2

Проведений інженерний аналіз показав, що Todoist, Motion та Sunsama використовують різні підходи до організації персонального планування, однак усі вони мають характерні архітектурні компроміси. Todoist оптимізує синхронізацію за рахунок batching та incremental sync, проте повна синхронізація великих наборів даних може супроводжуватися підвищеною затримкою. Motion застосовує фонову асинхронну обробку та багатокомпонентну хмарну інфраструктуру, що підвищує гнучкість системи, але одночасно збільшує кількість зовнішніх залежностей і складність контролю відмов. Sunsama значною мірою орієнтована на інтеграцію із зовнішніми календарними та task-management сервісами, тому стабільність і швидкодія системи залежать від доступності сторонніх API, rate limits та механізмів синхронізації.

У межах кваліфікаційного проєкту передбачено використання клієнт-серверної модульної архітектури з окремим модулем інтелектуального аналізу, PostgreSQL для основного зберігання даних, Redis для кешування та RabbitMQ для асинхронної взаємодії компонентів. Такий підхід дає змогу відокремити обчислювально складні операції адаптивного перепланування від синхронного API-рівня, зменшити затримку користувацьких запитів та підвищити відмовостійкість шляхом застосування retry-механізмів і черг повідомлень.

Обраний технологічний стек орієнтовано на контейнерне розгортання, автоматизацію CI/CD та подальший моніторинг. Це створює можливість незалежного масштабування компонентів, проведення інструментального тестування та контролю стану системи на етапі експлуатації. Таким чином, запропонована архітектура поєднує асинхронну обробку, кешування, модульність та автоматизовану інфраструктуру, що дає змогу мінімізувати частину обмежень, виявлених у проаналізованих аналогах.
